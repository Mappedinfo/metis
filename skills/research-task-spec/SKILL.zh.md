# 科研任务消歧与验收

将口头要求转成执行者与验收者能共同使用的任务约定。借鉴建筑任务书的需求表达、方案反馈与成果核对方法，重点解决“理解不同、重点遗漏、做完才发现不合格”。

## 何时使用

用户需要建立或接续科研任务约定、处理范围变化，或按约定验收时使用。简单明确的单步操作直接执行；仅初次拆解研究想法可用 `research-taskbook`，仅维护既定计划可用 `project-plan`。本技能负责约定与验收，领域方法由当前研究问题与适用能力决定。

## 方法

### 选择本轮工作

- **首次对齐**：从本轮获准材料建立任务约定，再推进已获准的工作。
- **执行或接续**：先读项目当前任务入口，只更新变化的需求、进展和证据。
- **验收**：按已接受的约定核对产物，交付逐项结果与真实缺口。

复用现有任务书、计划或 handoff 的对应区块。没有合适入口且需要跨轮跟踪时，创建一份 `TASK.md`；[任务约定模板](references/task-template.zh.md)供裁剪。短任务可在回复中完成对齐，无需建文件。将需求、进度、变更与验收留在同一入口，详细日志和结果只链接，不另建四套平行台账。

用户只要任务书时，交付任务书；用户已要求执行时，继续完成授权范围内的工作。任务约定本身不授予实验、资源使用或外部操作权限。

### 还原要求并处理歧义

先提取目标、对象、交付物、覆盖范围、重点、时间与资源约束，以及谁或什么规则判断合格。保留原要求的数量、范围和最新修订；将事实、用户要求、AI 建议、临时假设分开标注。

对可能影响结果的含义差异，写出“原话 → 可能解释 → 对执行或验收的影响”。重点检查指代、空间与时间范围、成果形式、质量含义、优先级冲突及资源边界。不要只靠模糊词检索判断歧义。

按影响处置：

- 可以从获准来源确定：直接核实并附来源定位。
- 例行、可逆且不改变目标的选择：声明采用的解释并继续。
- 会改变研究结论、必要覆盖、验收标准、成本上限或授权的缺口：集中询问必要问题，暂停依赖该答案的部分；继续独立工作。用户沉默不改变未决状态。

用简短复述或一个代表产物样例检验理解。例如，将“可靠的分析”展开为需要检查的数据口径、比较条件和结果证据。材料充分时直接推进；小样只用于对齐，后续仍完成已约定的全部覆盖。

### 写成能核对的条款

给需求稳定编号 `R1…`，记录来源与接受状态。每项需求包含：**动作和对象、交付物、约束、验收方法**。区分必须满足、偏好和可选建议；验收前不能将建议升为必需项。

验收可以是数值、功能用例、逐项清单、参考样例或有明确判断维度的人工评阅。数值写明单位、分母、比较基线和容差依据；“效果更好”“合理”“有创新”需要展开成具体判断，不能由 AI 任填阈值。

探索任务可把成功定义为完成覆盖、报告支持与反对证据、说明仍不能回答什么。将“研究流程与交付完成”同“假设得到支持”分别验收；阴性结果可以满足前者。尚未确定的阈值记录为建议或待定，必要时安排可获准的试点来估计，不能事后调低标准迁就结果。

只有任务涉及科学主张时才建 `C1…` 主张记录：主张的适用对象、比较或竞争解释、支持证据、可能推翻或削弱它的结果、当前状态。主张数量取决于接受的范围；不限制固定条数，不把待检验主张写成结论。质性或理论研究按材料反例、论证前提或推导检查选用标准。

### 安排重点并跟踪执行

将每项必需需求对应到任务 `T1…`，为任务记录输入、输出、依赖、验收与执行者；只详细展开有实际依赖的步骤。优先处理可能使后续失效的关键未知，同时保留其他已接受的交付范围。探索性的支线写清预期用途和结束条件。

有证据时才更新状态：`plan` 待执行；`doing` 正在执行；`done` 已通过对应验收；`blocked` 缺少具体条件；`drop` 已有依据取消。`blocked` 写最小解除条件；`drop` 写原因与依据，必需需求的取消须有相应用户修订。待验证、延期及局部产物均不等于完成。

只在关键决策、实验结果、失败路径、转向或需求变化时追加简短记录：时间、变更内容、依据、提出者、接受状态、受影响的 `R/T/C` 与下一步。只使用本轮和项目已获准材料，不自动扫描历史对话或整个代码库；AI 在授权内作出的例行选择可以记录，不逐条等待人工确认。

范围、数据、协议或标准变化时，保留旧版本定位，更新受影响的任务和验收；失效的旧证据改为待复核，继续有效的结果保留。不能用调整状态或删除条款制造完成。

### 按任务风险收集质量证据

沿 **需求 → 任务 → 产物 → 验收结果** 核对覆盖。证据定位到文件及相关表、图、字段、测试或运行记录；重要结果写明输入版本、计算方法、适用环境和实际检查范围。需要证明文件身份时保存哈希，文件存在和哈希相同各自只证明对应事实。

区分三层：成果是否齐全可用；方法与比较是否回答问题；主张是否被证据支持。能够运行、数值复算一致、统计显著，都不能单独替代后两层判断。重复运行按任务中的随机性、成本和数值容差安排，不强求所有方法逐字节一致。

按数据和问题选择质量检查。四个领域的[合成示例与选择依据](references/domain-demos.zh.md)只读匹配小节；不把所有空间检查、置换检验、负对照、显著性阈值或某个模型设为统一必需项。缺失证据阻止的是相应的完成或结论声明；无依赖的获准工作仍可推进。

### 验收与交接

逐项报告必需需求的 `通过 / 未通过 / 待验证`，附证据及范围；确实不适用的检查说明理由，不能用“不适用”消除必需需求。保留外部验收者的角色：助手核验通过不等于用户或评审已接受。

全部必需需求通过才能声明本任务完成；交付中同时写明未获支持的假设和结论边界。存在缺口时，明确已完成的部分、依赖受阻的部分和最小下一步。更新同一任务入口后交付，不为消歧本身增加无期限审查或强制审批轮次。

## 要求

- [B] R1 保留接受的范围、数量与来源，区分要求、事实、建议及假设；验证：与当前要求和旧约定逐项核对。
- [B] R2 重要歧义有处置依据，关键缺口只阻塞依赖部分；验证：约定标明采用的解释、待答问题、受影响任务和解除条件。
- [B] R3 必需需求可追溯到任务、产物及验收方法，阈值有依据或明确待定；验证：逐项检查需求到证据的覆盖，计划阶段核对计划本身。
- [B] R4 变更保留继续有效的要求和旧版本定位，不以改状态制造完成；验证：变更记录能解释受影响项、保留项和需复核的证据。
- [B] R5 按证据范围验收，区分研究流程完成、假设支持与外部接受；验证：各项结果有证据或缺口理由，未支持假设不会被改写为支持。
- [B] R6 收尾为接受的任务要求及本节适用要求记录 done、blocked 或 n/a，并给出证据或理由；验证：同一入口或已有验收台账覆盖全部必需项，n/a 不豁免用户必需结果。
- [A] R7 仅保留有用的重点、依赖与关键事件，复用现有入口；验证：没有为短任务强建文件，也没有重复的状态台账。

## 何时停止

- 按本轮模式完成约定、变更或验收交付，且适用的 [B] 要求都有通过证据后停止。只要求任务书时，验收任务书，后续研究执行保持未执行；要求执行时仍须完成已接受范围。
- 本技能的约定与验收检查每次调用各做一轮；发现具体缺陷时最多做一轮针对性修正并复核受影响项。用户已给检查预算时沿用该预算；该次数不限制已授权研究工作的规模或替代领域运行预算。
- 缺少关键输入、权限或预算用尽时，交付已完成项、未完成项和最小解除条件；受阻必需项保持 blocked。独立可做的授权工作继续推进，不重新开启已完成阶段。

## 交付契约

1. 一份更新后的任务约定或相应项目现有区块：目标范围、带来源的需求、歧义处置、任务依赖与重点。短任务可直接在回复中完成。
2. 本轮验收与变更记录：逐项结果、实际证据和范围、需复核项、主张状态及外部验收状态；与原入口合并维护。
3. 接受的任务要求与适用 R1–R7 的执行台账：done / blocked / n/a、证据或理由、停止条件和剩余工作的最小下一步。无需为这些字段另建文件。

## 来源

本技能由获所有者授权的任务书工作流重新编写为 metis 通用方法，采用建筑任务书的需求表达、反馈与成果核对类比。领域示例均为合成；没有将未核验的外部论断或建筑技术数值作为行业规范。原创建与本次提取的个人记录保留在调用方，不随公共技能分发。

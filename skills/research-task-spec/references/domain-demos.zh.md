# 领域合成示例

以下均为虚构任务，用于示范如何选择歧义、重点与验收；没有实际数据、运行或研究结论。路径和阈值是待商定的示例，不能当成现有项目事实。按当前领域只读匹配小节。

## 地理科学：降雨与滑坡的关联

**收到的任务**：“比较两类降雨资料，看看哪一种更能解释滑坡，结果要可靠。”

**关键歧义**：资料比较针对历史事件解释，还是对未见事件预测？分析单元是事件、坡单元还是网格？降雨累计窗口相对滑坡发生时间怎样定义？这些解释改变样本与验证设计，应从已有协议核实或集中询问。文件命名和图表配色可按项目惯例直接处理。

**可以前置完成**：列出已提供数据的空间范围、时间覆盖、单位、缺失和事件标识；标明尚未确定的分析口径，暂不据此宣布某资料更好。

| 需求 | 可核对的交付 | 验收依据 |
| --- | --- | --- |
| R1 比较资料可比性 | 数据覆盖表与差异说明 | 单位、时间口径、空间支持范围与缺失处理均可追溯；无法对齐的部分单列 |
| R2 完成约定比较 | 方法、比较表与不确定性说明 | 在选定的共同评价范围下使用相同基准与样本规则；若目标为外推预测，验证划分与目标中的空间或时间泛化相符 |

**重点与检查选择**：只有涉及空间叠加时检查 CRS、空间覆盖与对齐；只有像元数据才检查栅格相关项。降雨作为先于事件的解释量时核对时间顺序；对于预测任务，避免使用预测时不可获得的信息。空间或时间依赖影响评价时，设计相应划分、稳健性或不确定性分析，不把任意随机划分直接解释成空间泛化能力。

**结束条件**：完成约定比较并如实报告差异；证据不足以分出高下时，比较任务仍可完成，优劣结论保持不确定。

## 城市科学：绿地配置与热环境

**收到的任务**：“做城市热岛与绿地配置分析，说明绿地的影响。”

**关键歧义**：“影响”指描述性关联还是因果效应？热环境指地表温度、气温还是热暴露？研究地区、季节、观察单元是否已约定？不将“影响”自动改写成因果结论，不将建筑采光或一般规划指标当作本任务阈值。

**任务化示例**：若用户接受的是关联分析，将 R1 写为“按约定空间与时间口径建立分析表，报告绿地变量与热环境指标的关联、适用范围和不确定性”；R2 写为“检查选定尺度及关键处理选择对结论的影响，交付结果表与方法说明”。变量、尺度、区间方法和覆盖数量由研究问题、已接受协议与数据可得性决定。

**重点与检查选择**：核对观测单元、空间匹配、分母与变量定义；聚合尺度与边界可能影响结论时检查尺度敏感性；残差空间依赖只在适用模型及推断目标下诊断。残差存在空间自相关提示模型、标准误或研究设计需要复核，不能据此自动指定空间滞后模型、空间误差模型或 GWR。若要求因果判断，先明确识别依据、混杂处理和可支持的范围。

**主张示例**：C1 为“在所研究的地区与时期，绿地指标与地表温度存在约定方向的关联”，保持待检验。方向不稳定、控制或尺度变化使关联消失等结果会削弱该表述；关联稳健也不单独确立因果。

**变更示例**：用户将交付从关联分析改为政策因果效果评估。记录其来源、受影响的 R1/C1、需新增的识别工作与资源缺口；原数据质检仍有效，原关联证据不再足以验收因果效果。

## GeoAI：跨城市遥感分类

**收到的任务**：“训练一个跨城市也准的分类模型，优于当前 baseline。”

**关键歧义**：“跨城市”是完全未见城市，还是目标城市有少量标签？类别、预测单元和指标如何确定？已有数据和训练授权是否包含所需资源与运行预算？模型名称、城市数、提升幅度、随机种子数量均不从示例自动补齐。

| 需求 | 任务与证据 | 验收依据 |
| --- | --- | --- |
| R1 明确泛化评价 | T1 记录城市、时间与样本划分，产出 split 清单 | 符合已接受的部署情境；核对跨划分的重复、重叠及与问题相关的空间信息泄漏 |
| R2 与 baseline 公平比较 | T2 在约定数据、标签及资源条件下运行，保存配置和指标计算 | 预处理拟合与模型选择使用允许的数据；测试集保持其既定评价角色；方法差异与预算差异报告清楚 |
| R3 交付可核验结果 | T3 交付模型、评价表与运行记录 | 指标含聚合方式、分母或权重、分城市结果及适用的不确定性；复算范围和数值容差明确 |

**证据不足的处理**：baseline 的运行记录缺失时，可以准备数据核对和评估流程；改进结论标为待验证。确实需要并获准重新运行后再补证据，不能把记忆中的数值或模拟结果当 baseline。

**结束条件**：若用户仅要求完成公平比较，模型未超越 baseline 也可完成任务；若明确要求达到约定性能，未达到时该项未通过，报告结果和缺口，不更改原目标。

## 计算机科学：检索系统原型与性能比较

**收到的任务**：“做个可演示的检索 demo，再验证新索引更快、质量不掉。”

**关键歧义**：演示的必要用户动作与输入是什么？“更快”测构建、吞吐、单次查询还是特定分位延迟？“质量不掉”用什么相关性指标或功能用例？数据规模、硬件、并发和缓存条件是否已固定？先落实这些含义，阈值可以引用已有基准或明确提案。

**分开验收**：R1 的原型按完整用户路径核对，例如输入查询、显示结果、空结果和错误反馈。R2 的性能结论使用相同工作负载和明确测量条件，报告重复测量的波动；质量按已接受的判定方法核对。界面能操作只支持 R1，不能替代 R2；没有空间数据时无需 CRS、MAUP 或空间置换检查。

**跟踪示例**：新实现只在暖缓存下更快，将观察条件和对应结果位置记入实验事件；若先前主张包含冷缓存，则该主张尚未通过。可保留已实现功能和已核对的暖缓存结果，继续获准的缺口检查。

**结束条件**：功能与比较分别给结果。超出已接受资源的扩测记录为建议；核心用例或必需基准缺失时报告未完成部分，不能用更多截图替代。

## 方法来源的范围

这些示例为 metis 任务约定工作流编写，使用建筑任务书的需求表达、方案反馈和成果核对类比。示例不建立建筑规范或具体领域技术阈值，实际方法与验收条件取当前研究问题和已接受协议。

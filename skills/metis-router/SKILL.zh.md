[English](SKILL.md) 是执行依据；本文件为可编辑的中文译本。

# metis-router

将任务路由到 metis 技能集合：同一写作交付保留一个场景负责人，真正跨产物的任务
按阶段选择一个主技能；每阶段至多两个辅助技能，
通过 `uses:` 引用接入共享样式 profile，并明确可验证的产出物。适用于跨越多个
能力域的请求（如“找论文、制图、做幻灯片”）、技能职责重叠而难以选择的情况，
以及需要多个技能保持交付物样式一致的任务。单一能力即可完成的任务直接加载
对应技能，无需使用本路由。

## 功能

把 metis 技能组合为一个连贯的任务。输入是跨越多个能力域的任务，输出是有界
执行计划：由哪个技能主导，至多哪两个技能辅助，应用哪些共享 profile，以及
通过什么产出物证明任务已完成。

用户只要求计划或路由建议时，交付路由说明后停止。请求包含实际执行时，在
用户授权的范围内执行各阶段。

## 何时使用 / 不使用

请求包含多个阶段或产出物类型（如“收集 X 的资料、分析数据，再做一份幻灯片”）、
两个技能声明了相同触发条件而需要说明选择理由，或不同技能的视觉产出必须
呈现为同一套作品时，使用本技能。

一个技能显然足以覆盖请求时，**不要**使用本路由：单一能力任务不需要增加
路由层。不要用本技能重新规划已经获准的计划。

## 方法

### 0. 保持科研任务约定明确

科研任务存在影响结果的歧义、范围变化或持续验收需求时，使用
[research-task-spec](../research-task-spec/SKILL.zh.md) 作为核心任务约定能力。
复用已经接受的约定，只更新受影响项，不重开已定选择或新增审批轮次。
需求 → 任务 → 证据的对应关系随项目跨阶段保留。任务约定本身是交付时由它主导；
领域主技能确有缺口时才将它作为辅助，仍遵守每阶段的技能数量限制。

`research-taskbook` 保留初次想法转任务书的职责；`project-plan` 维护已明确的执行计划。
清楚的单步任务直接执行。任务约定不改变授权，也不替代实质研究方法。

### 1. 先确定交付负责人，再识别未完成工作

同一写作交付按场景选择持续负责的主技能：`source-brief` 负责已有材料的简报、
长文或选择性技术史，`concept-note` 负责概念笔记。其他已具备完整交付契约的写作
场景同理。负责人内部复用[共同写作判断](../source-brief/references/writing-foundations.md)
和适用的审校方法；情境、组织、起稿、审校不是四个轮流接管同一文章的场景。
只请求提纲、诊断或审校时，选择覆盖该操作的入口，不追加全文写作。

真正跨产物、独立分析或实验的任务，仍按资源生命周期识别先决工作与阶段负责人：

```
acquire → analyze → compose / visualize / present → build
```

不在同一写作场景内的**最早一个必需且尚未完成阶段**确定当前阶段主技能。
同一文章若需要获准的资料补充，该工作保留先决条件和证据，不因读取辅助方法就
交出文章最终责任。检查已有完成证据：持有
十篇 PDF 能证明已获取资料，不能证明已完成分析。“根据这十篇论文制作幻灯片”
在论文主张仍需阅读和评估时从 `analyze` 开始；已有充分且有来源依据的综合
分析时，可以从 `present` 开始。“研究 X 并作汇报”在资料尚未获取时从
`acquire` 开始。

### 2. 每阶段一个主技能，至多两个辅助技能

- 当前阶段的产出物恰好由**一个主技能**负责。
- 至多**两个辅助技能**补足主技能确实缺少的能力，例如以 `analyze` 为主，
  由 `acquire` 检索和 `visualize` 制图辅助。若需要第三个辅助技能，应拆分阶段。
- 真正跨产物的阶段结束时重新判断职责。第一阶段的辅助技能可以成为第二阶段的主技能；
  同一写作场景的内部步骤保持原负责人。

共同的情境、组织与审校模块是内部指导，不作为额外场景或占用辅助名额；独立
检索、专业分析、实验和图件制作仍按实际能力计数。不要把独立工作改称模块来规避限制。

数值图形按输入和实际任务选择：`table-chart` 负责其渲染范围内的准备好的 CSV
图表；`scientific-plot` 负责数组、计算结果、教学演示和自定义面板。尚未解决的
研究推断留在分析阶段。个人风格须有适用的用户／项目要求，不能仅凭 Matplotlib
或项目名称选择。单一绘图任务可以直接读取对应技能。

按实际输入选择下一阶段：`data-preparation` 解决数据单位与转换，`exploratory-analysis` 诊断准备后数据，`experiment-run` 执行明确协议，`run-review` 核验已记录的运行产物。`taskbook-reproduce` 负责复现准备，不能据此声称完成运行。单篇阅读由 `taskbook-interpret` 承接，已确定多篇集合的比较由 `literature-synthesis` 承接。已有充分多来源材料进入 `source-slides`；单篇论文中文组会汇报进入 `taskbook-slides`。方法和机制图进入 `research-diagram`。保留有效的用户点名；能力缺失时报告其名称，不静默替换。

委派时把所选技能入口、项目 profile、输入／分析边界、完整输出要求和相关检查
传给工作单元。工作单元执行前读取必需指南，协调者检查整合导出。写出技能名称
或收到成功的进程结果，不能证明指南已加载或最终图件质量合格。

### 3. 通过 profile 统一样式

对于每项视觉产出，检查对应技能 frontmatter 中的 `uses:`，并从当前项目根目录
读取 `profiles/<name>.yaml`。这些标识符是逻辑依赖，不是相对于已安装
`SKILL.md` 的路径。项目需要将 profile 与技能分别安装；可通过
`metis-os profiles install` 安装。源码仓库和已发布 CLI 的用法见公开的
[profile 安装指南](https://github.com/mappedinfo/metis/blob/main/profiles/README.md)。

为每项产出物及其受众保留完整且合适的 profile：投稿图片使用
`profiles/journal`，相应汇报幻灯片使用 `profiles/deck`。协调二者共享的调色板
和字体角色，同时保留各自的字号、尺寸、分辨率和导出格式。需要样式变体时，
将其记录为具名 profile；不要用最后一个交付物的 profile 替换全部 profile。

在任务授权范围内安装缺失的 profile，并保留项目现有样式。无法安装或与已有
文件冲突时，先报告受影响的标识符和解除阻塞的条件，再制作依赖它的视觉产出。
如果没有合适的现有 profile，指出缺口，并在任务范围内提出具名 profile。
不要在技能内部自行定义调色板。

### 4. 每阶段锚定一个产出物

每个阶段都以可验证的产出物结束，该产出物应在技能 frontmatter 的 `artifacts`
及输出契约中声明：下载的 PDF、表格、图文件、幻灯片、软件包，或包含决策与
验收标准的计划说明。根据用户要求的结果检查产出物。计划可以完成规划请求，
但不能证明计划中的执行已经发生。

前端任务使用已安装工具，完成相关构建、类型／语法检查及必要的已有轻量测试后交付。界面由用户手动检查；仅在用户明确要求交互或视觉验收时，才追加浏览器／computer use、逐项点击、截图或视觉回归。保留既有功能与测试、修复真实失败，不隐藏错误，不扩展大型 lint 系统，也不为检查安装 Torch 等无关重依赖。简短报告实际检查及「未做界面验收」；代码通过不证明交互、视觉或真实数据链路已验证，未请求的界面检查不阻塞代码交付。科学、数据完整性、图件、幻灯片及部署的专门要求保留各自范围。

使用随技能提供的[需求台账](templates/requirements-ledger.zh.md)，记录已接受
的任务要求和各活跃技能的 Requirements 条目。保持 ID 稳定，使每项结果都能
追溯到所满足的检查项。工作过程中更新台账；收尾时，每项都应标为 `done`、
`blocked` 或 `n/a`，并附证据或理由。只有声明的验证通过后才能标记 `done`。
`n/a` 必须有基于范围的理由，不能免除用户要求的必需结果。仅规划的请求应
评估计划本身的要求，并将下游执行明确记为尚未执行，而非已完成。

### 5. 并行审查、限定范围修复（map–freeze–reduce）

对语料库、文稿或代码库进行审查与修复时：

1. **Map**：列出独立的检查维度；每个维度执行一次有界的只读审查，运行环境
   支持时并行执行。每项审查有自己的轮次预算，只返回发现，不进行修复。
2. **Freeze**：将发现合并为去重的问题台账。每项注明严重程度和声明的写入
   范围。冻结后的台账是本轮修复唯一的事实依据。
3. **Reduce**：仅对写入范围不相交的任务并行修复；有重叠的任务排队执行。
   每个修复任务只验证自己负责的台账条目。恰好执行一轮有界复审后停止，
   报告剩余问题，不继续追逐修复。

修复范围由冻结台账决定。将发现关联到需求台账；问题清单不能替代证明已接受
任务要求得到满足的证据。

### 6. 独立生产：分配前先检查

异构批次或多项可独立验收产物，在分配代理前读取共享的
[并行生产指南](references/parallel-production.zh.md)。核对代表输入，冻结共同契约，
再确定单元、独占写入、已观察资源上限、失败隔离与分阶段增量重跑。保留接受的
范围和最终覆盖检查；没有获准的空闲代理容量时，同样的单元顺序执行。

单能力生产者也可按需读取本指南，不必为此调用路由或重写接受计划。
`project-plan` 引用同一规则，不另维护生产政策。

需要边生产边浏览时，同时应用该指南的持续生产契约；一个长任务也适用。
先建立稳定读取路径与逐项发布，再等待全量覆盖；生产代码的在途修改不进入
正在服务的读取路径。原最终范围与验收要求继续保留。

## 要求

- [B] R1 同一写作交付有持续负责的场景主技能；跨产物任务的阶段主技能对应
  最早未决工作——验证：路由说明列出负责人、交付边界及尚需完成的先决工作和证据。
- [B] R2 每个 agent、每阶段至多两个辅助技能——验证：辅助技能列表最多两项，
  每项注明所补足的能力缺口。
- [B] R3 每项产出物分别保留 profile，不混并受众——验证：每项产出物注明自己的
  profile，或明确不使用 profile。
- [B] R4 每个阶段锚定一个声明的产出物——验证：计划按制作顺序列出预期产出物。
- [A] R5 审查与修复遵循 map–freeze–reduce——验证：输出中明确列出冻结的问题台账。
- [B] R6 遵守停止规则和预算上限——验证：收尾时说明触发的停止条件；预算耗尽
  时列出已完成项、未完成项和最小解除阻塞条件。
- [B] R7 覆盖全部已接受的任务要求和适用的技能要求——验证：需求台账记录每项
  的状态与证据或理由；宣布任务完成前，所有适用的阻断项均须完成。

- [B] R8 适用的批量生产已核对分配边界——验证：分配代理前，单元表列明独立
  产物、共享契约、实际写入／资源证据、失败隔离和重跑范围；最终整合覆盖全部
  接受单元。单项或紧密耦合工作记录不适用生产划分的理由。

- [B] R9 并行于生产的结果审查保持可用——验证：任务需要持续浏览时，执行
  指南规定的故障／兼容场景，核对持续访问与增量更新；前端检查采用上文默认值。只规划时将这些检查标为
  尚未执行；无同时浏览需求时按范围标 n/a，不为满足此项新造工作台。

- [B] R10 适用的科研任务约定保持可追溯——验证：影响结果的歧义、变更及验收
  由既有约定或 research-task-spec 处理，需求跨阶段对应任务与证据；清楚的单步
  任务按范围标 n/a，不增加规划。

## 何时停止

- 仅规划任务已交付路由说明；执行任务的最终产出物已存在，且符合对应技能的
  输出契约。两种情况下，需求台账内所有适用的阻断项都必须有验证通过的证据。
- 集合中没有技能覆盖某项必需能力：按 category 和 domain 标签报告能力缺口，
  然后停止。这是可贡献的候选项，不是允许自行临场发挥的授权。
- 声明的预算（轮次、重试次数、队列大小）已耗尽：报告已完成项、未完成项和
  最小解除阻塞条件；未解决的必需项保持 `blocked`，不得宣称全部完成。
  不要重新打开已完成的阶段。
- 用户缩小了范围，或证据确实存在歧义：用范围明确的问题请人判断，不要无休止
  地重新路由。

## 输出契约

交付一份用户一次阅读即可核对的路由说明：

1. **主技能**及其负责的完整场景交付，或跨产物阶段；内部步骤不另造负责人。
2. **辅助技能**（≤2），以及各自补足的具体缺口。
3. 每项产出物的 **profile**，注明共享角色及具名变体。
4. 各阶段按顺序列出的预期**产出物**。
5. **能力缺口**：没有技能覆盖的能力，以 category + domain 标注。
6. 对审查与修复任务，冻结的问题台账本身也是具名交付物，持续保留至收尾。
7. 使用随附模板的**需求台账**，每项均有状态、证据或理由，并说明停止条件。
   预算耗尽时还须列出已完成项、未完成项和最小解除阻塞条件。

8. 适用的批量生产包含并行生产指南规定的共享契约和单元表，注明分配检查及未决单元。
   持续浏览另列稳定读取路径、更新机制及实际可用性检查，计划与执行分别记录。

9. 适用科研任务的约定入口及其需求、变更、验收记录链接。

执行请求需要实际执行计划，并验证各阶段的具名产出物。规划请求以路由说明及
其需求台账为最终交付物；下游执行保持尚未执行状态。
